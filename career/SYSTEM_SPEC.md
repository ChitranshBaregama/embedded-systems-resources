# Firmware preparation operating specification

Canonical repository: embedded-systems-resources. The reference library and runnable examples remain intact. Firmware-Interview-Prep is migration input, not a second progress database.

The journey is Learn → Practice → Code → Debug → Build Projects → Contribute Open Source → Prepare Interviews → Prove Readiness. Google-class firmware roles are an aspirational benchmark, not a claim that this is an official Google curriculum or a hiring guarantee.

## Ownership of learning

For scored practice, the learner writes every implementation line. The coach supplies contracts, tests, progressive hints, adversarial review, and interview follow-ups. Do not provide a final implementation before an attempt and an explicit request. Existing solved reference material remains available, but consulting it makes that attempt assisted. Infrastructure, test harnesses, and reference examples are not learner performance.

Never infer progress from generated files, commits, or passing infrastructure CI. Initial progress is Unseen; unknown metrics remain blank. Declare readiness only from recorded evidence.

## Sessions

“Start today’s firmware session” means inspect the progress ledger, due revisits, weak topics, and gate evidence; choose a small set in difficulty order; provide requirements before hints; review the user's code; test boundaries; ask follow-ups; record the actual outcome and next review. Gate advancement is a separate evidence review, never automatic from count.

Default session: 15 min retention, 15 min quick drills, 45 min one coding task, 25 min firmware/debugging/design, 15 min testing and oral explanation, 5 min logging. Stop at 120 minutes. On a project day replace the coding/design blocks with 70 minutes of project work. Protect work, GATE study, exercise and sleep rather than borrowing time invisibly.

For “Start today’s 45-minute coding session”: 5 min contract, 25 min independent attempt, 10 min tests/review, 5 min notes and follow-ups. Unfinished work remains Attempted.

## Evidence and privacy

Keep only public, sanitized learning evidence here. No employer firmware, private logs, customer identifiers, keys, tokens or confidential diagrams. Project claims distinguish host-tested, emulator-tested, compile-only and measured-on-board evidence. Obtain explicit instructions before sending messages or submitting contributions to third-party maintainers.
